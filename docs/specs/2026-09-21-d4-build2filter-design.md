# d4-build2filter — спека

**Дата:** 2026-09-21
**Версия:** 2 (переписана после разведки, см. раздел 10)
**Статус:** на вычитке у владельца

---

## 1. Что это и зачем

Страница на GitHub Pages. Вставляешь **ссылку на билд с d4builds.gg** — получаешь **лут-фильтр
для Diablo 4**:

- **код импорта** — строка, которую на ПК вставляют в игру за минуту;
- **чеклист** — пошаговый список правил и галочек для Switch 2, где вставить код нельзя.

Ссылку на страницу можно дать друзьям: они вставляют свои билды и получают свои фильтры.
Ничего не устанавливается, сервера нет, платить не за что.

### Критерий успеха (проверяемый)

> Сгенерированный код вставлен в игру на ПК, затем **экспортирован из игры обратно**, и
> инструмент, разобрав этот экспорт, показывает **ноль расхождений** с тем, что собирался
> закодировать.

Сверяем не с нашим представлением о формате, а с тем, что игра реально приняла и вернула.
Второй, более слабый критерий — `selftest.html` прогоняет эталоны «закодировал → разобрал →
сравнил» и светится зелёным.

### Чего инструмент не делает

- **Не импортирует билд в игру.** Такой возможности в Diablo 4 нет: умения, аспекты и вещи
  набиваются руками. Фильтр управляет только тем, что видно на земле.
- **Не фильтрует по закалке и аспектам.** Это не свойства падающей вещи — их наносят позже
  у Кузнеца и Оккультиста.
- **Не пытается быть умнее билда.** Переносим то, что в билде написано.

---

## 2. Главное правило безопасности

> **Прячем — только по грубым признакам: редкость, сила предмета, тип вещи.**
> **Красим — по аффиксам.**

Ошибка в таблице id аффиксов **физически не может спрятать нужную вещь**: худшее — вещь не
подсветится.

Второе правило: **инструмент не молчит о непонятом**. Свойство, которому не нашлось
соответствия, попадает в видимый список «не перенесено», а не исчезает тихо.

## 3. Устройство

```
  пользователь вставляет ссылку
            │
            ▼
   src/resolve.js   ── длинный id из ссылки, либо поиск в data/meta-builds.json
            │
            ▼
   src/fetchBuild.js ── GET в открытую базу Firestore  →  BuildProfile
            │
            ├─ src/rules.js     → набор правил фильтра
            ├─ src/encode.js    → protobuf → base64 → код импорта
            ├─ src/decode.js    → разбор обратно (самопроверка перед выдачей)
            └─ src/checklist.js → чеклист для Switch 2
```

Всё выполняется в браузере посетителя. Ни один запрос не идёт на наш сервер, потому что
сервера нет.

### 3.1. Разбор ссылки (`src/resolve.js`)

Два вида адресов:

| Вид | Пример | Как решается |
|---|---|---|
| с идентификатором | `d4builds.gg/builds/87dc0249-02db-4eb0-b9fc-c2acfb012fa6/` | берём id прямо из адреса |
| короткий (витринные билды) | `d4builds.gg/builds/blazing-scream-warlock-leveling/?var=0` | ищем в `data/meta-builds.json` |

Билды, которые игроки создают сами, всегда имеют адрес первого вида — то есть у друзей всё
работает сразу. Короткие адреса только у витринных билдов сайта.

**Почему нужна карта.** Поиск по названию в базе запрещён правилами доступа — проверено,
отвечает «нет прав». Читать напрямую можно только документ по идентификатору.

**Если короткого адреса нет в карте** — понятное сообщение: «этот витринный билд появился
после последнего обновления карты; карта обновляется раз в сутки, либо откройте билд и
скопируйте адрес с длинным идентификатором».

### 3.2. Карта витринных билдов (`data/meta-builds.json`)

Простой словарь `короткий-адрес → идентификатор`.

Обновляется **задачей GitHub по расписанию** (раз в сутки): она собирает список витринных
билдов, для каждого забирает `seoId` из служебного файла `page-data.json` и коммитит
обновлённую карту. Для публичных репозиториев это бесплатно.

Задача **не трогает ничего, кроме этого файла**, и падение задачи не ломает страницу — она
просто работает со вчерашней картой.

### 3.3. Чтение билда (`src/fetchBuild.js`)

Один запрос:

```
GET https://firestore.googleapis.com/v1/projects/d4builds-a3254
        /databases/(default)/documents/builds/<id>
```

Публичный, без ключей, с разрешёнными межсайтовыми запросами — **проверено с постороннего
домена: 200, 94 КБ**. Это тот же запрос, который делает сам сайт d4builds, когда вы открываете
билд в браузере.

Из документа берём:

| Поле | Что это |
|---|---|
| `class`, `season` | класс и сезон билда |
| `name`, `variantName` | название и вариант |
| `newStats` | **главное**: по каждому слоту список желаемых свойств обычными словами |
| `gear` | аспекты по слотам |
| `temperingStats` | закалка (показываем, но в фильтр не переносим) |
| `greaterAffixes` | какие свойства билд хочет великими |
| `charms`, `soulShards` | талисманы и осколок — для будущих версий |

Пример реальных данных из билда владельца:
`"Ring 1": ["Willpower","Maximum Life","Critical Strike Chance",null,"Critical Strike Damage Multiplier"]`

Пустые места (`null`) — слоты, которые автор билда не заполнил; они пропускаются.

**Вежливость к чужому сервису:** результат кладётся в память браузера на сутки, чтобы
повторные открытия того же билда не били по базе; внизу страницы — ссылка «данные билда
с d4builds.gg» с указанием автора билда.

**Единая точка отказа.** Если d4builds закроет публичное чтение, страница перестанет забирать
билды. Тогда остаётся ручной ввод свойств. Это записано честно: другого пути у статической
страницы нет.

### 3.4. Формат BuildProfile

Промежуточный вид, граница между чтением и сборкой правил. Версионируется.

```json
{
  "schema": 1,
  "source": "https://d4builds.gg/builds/<id>/",
  "buildId": "87dc0249-02db-4eb0-b9fc-c2acfb012fa6",
  "name": "Blazing Scream Warlock Leveling (S15)",
  "variant": "Standard Build",
  "class": "Warlock",
  "season": 15,
  "slots": [
    { "slot": "Ring 1", "itemType": "ring",
      "affixes": ["Willpower","Maximum Life","Critical Strike Chance",
                  "Critical Strike Damage Multiplier"],
      "greater": ["Critical Strike Damage Multiplier"],
      "tempering": ["Shadow Damage (Elemental Finesse: Night - Offensive)"],
      "aspect": "Aspect of Peril" }
  ]
}
```

`tempering` хранится **намеренно**, хотя в фильтр не идёт: страница показывает его отдельным
блоком «это не переносится, вот почему», чтобы было видно — строку не потеряли, а сознательно
отложили.

### 3.5. Сборка правил (`src/rules.js`)

**Группа А — база, всегда:**

1. `Мифики` — перекрасить: `ITEM_PROPERTIES(mythic)` + `ITEM_RARITY_MATCH(unique|mythic)`
2. `Древние уникумы и мифики` — показать: `ITEM_PROPERTIES(ancestral)` + `ITEM_RARITY_MATCH(unique|mythic)`
3. `Апгрейд кодекса` — перекрасить зелёным: `CODEX_UPGRADE_CHECK`

**Группа Б — подсветка под билд:**

Для каждого слота — своё правило:

```
имя:       "<Билд> · Ring"
видимость: RECOLOR (по умолчанию оранжевый FFFF8C1A, меняется на странице)
условия:   ITEM_TYPE_MATCH(типы слота)
           HAS_REQUIRED_AFFIXES(id аффиксов слота, минимум N)
```

Цвет один на всю группу, чтобы «оранжевое» читалось как «под мой билд» и не спорило
с зелёным от кодекса.

`N` — порог совпадения, ползунок на странице, **по умолчанию 2**. При 1 подсветится почти
всё, при 4 — почти ничего.

Слоты с одинаковым типом вещи и одинаковым набором свойств **склеиваются** (обычно Ring 1
и Ring 2). Ориентир — не больше 14 правил на фильтр.

**Если id типа вещи не подтверждён** — условие `ITEM_TYPE_MATCH` из правила выбрасывается,
правило становится общим: «любая вещь, где совпало N свойств». Подсветится лишнее, но
ничего не потеряется. Страница предупреждает.

**Группа В — прятать мусор, три уровня:**

| Уровень | Что прячет |
|---|---|
| Мягкий (по умолчанию) | недревние обычные и магические; магические и редкие талисманы |
| Средний | плюс недревние редкие, затем недревние легендарные |
| Строгий | плюс недревние уникумы и вещи без великих аффиксов |

Условия только `ITEM_RARITY_MATCH`, `ITEM_POWER_RANGE`, `ITEM_TYPE_MATCH`,
`GREATER_AFFIX_CHECK`. Аффиксов в правилах пряток нет **никогда**.

### 3.6. Кодировщик (`src/encode.js`)

Protobuf, упакованный в base64. Схема собрана из опубликованного описания и **проверена
разбором реального рабочего кода** — готовый фильтр maxroll разобран по байтам при
проектировании.

```
Filter
  1  repeated Rule   rules
  2  string          name
  3  int32           = 3
  4  int32           = 3

Rule
  1  string          name
  2  enum            visibility   0=SHOW 1=HIDE_TEXT_LABEL 2=RECOLOR 3=HIDE_ALL
  3  fixed32         color        ARGB, старший байт FF   (только при RECOLOR)
  4  repeated Cond   conditions
  5  bool            enabled

Cond
  1  enum   type     0 ITEM_POWER_RANGE   1 ITEM_RARITY_MATCH   2 ITEM_PROPERTIES
                     3 CODEX_UPGRADE      4 GREATER_AFFIX_CHECK 5 ITEM_TYPE_MATCH
                     6 HAS_REQUIRED_AFFIXES  7 HAS_OPTIONAL_AFFIXES
                     8 IS_SPECIFIC_UNIQUE    9 TALISMAN_SET_BONUS
  2  repeated fixed32  params1   (id аффиксов / типов / уникумов)
  4  varint            value1
  5  varint            value2
```

**Помечено `// UNVERIFIED:` и подтверждается на круге сверки:**

- номера полей `value1` / `value2` для условий, кроме четырёх встретившихся в образце;
- граница «недревнего»: описание набора maxroll говорит «851», в его же коде лежит **850**.
  До сверки берём 850, как в живом коде.

### 3.7. Чеклист для Switch 2 (`src/checklist.js`)

Из того же набора правил — человеческая инструкция: по правилу на блок, внутри «Видимость →
Скрыть всё», «Item Rarity Match → отметить Обычные, Магические» и так далее.

**Оговорено прямо:** подписи пунктов меню взяты из описаний формата, а **не с экрана Switch 2**
— консольная версия вышла 15 сентября 2026, её интерфейса я не видел. Первый чеклист владелец
сверяет с экраном и правит подписи, после чего они фиксируются в `data/ui-labels.json`.
До сверки чеклист несёт предупреждение в шапке.

## 4. Таблицы id

Самое хрупкое место. Таблиц две, режим проверки общий.

### 4.1. Типы вещей (`data/type-ids.json`)

Нужны и для пряток, и для правил под слот. Источник — экспорт из игры фильтра с одним
отмеченным типом. Пока тип не подтверждён, он помечен `unknown`:

- в **подсветке** условие о типе выбрасывается (безопасно, см. 3.5);
- в **прятках** правило не создаётся вовсе и уходит в список «не перенесено» — иначе
  «скрыть обычные и магические» заденет талисманы, которые прятать не хотели.

### 4.2. Аффиксы (`data/affix-ids.json`)

Строки вида
`{"name": "Critical Strike Chance", "id": 2620563, "verified": "2026-09-21", "source": "game-export"}`

Три источника, по убыванию доверия:

1. `game-export` — владелец собрал в игре фильтр с одним аффиксом, экспортировал, инструмент
   вытащил id. Это ground truth.
2. `community-s13` — из открытого генератора (77 id, 13 сезон), **со ссылкой на автора**.
   Считается гипотезой, не фактом.
3. `unknown` — соответствия не нашли.

На странице: группа 1 зелёная, группа 2 **жёлтая с подписью «не подтверждено на 15 сезоне»**,
группа 3 отдельным списком «не перенесено».

### 4.3. Режим сверки (`verify.html`)

Вставляешь код, экспортированный из игры, — инструмент разбирает его и говорит по каждому
аффиксу «совпал» / «другой id, вот новый» / «такого не было». Обновлённые строки скачиваются
готовым файлом.

Таблица чинится по одному аффиксу за раз, и каждая починка оставляет след в `AFFIX-IDS.md`.

**Про лицензию:** в открытом генераторе лицензия не указана, поэтому **код оттуда не
копируется**. Берём только числовые соответствия как справочные сведения, со ссылкой на
автора, и каждое помечено как неподтверждённое. Кодировщик пишется с нуля по схеме формата.

## 5. Поведение при ошибках

| Ситуация | Что делает |
|---|---|
| адрес не с d4builds.gg | «нужна ссылка на билд с d4builds.gg», пример правильной |
| короткий адрес не найден в карте | объясняет про карту и как взять адрес с идентификатором |
| база вернула 403 или 404 | «билд не найден или закрыт автором» |
| база недоступна | «d4builds сейчас не отвечает, попробуйте позже», старые данные из памяти браузера, если есть |
| свойство не найдено в таблице | в список «не перенесено», код всё равно собирается |
| ни одного переносимого свойства | код не собирается, объяснение почему |
| код собран, но разбор обратно не совпал | код **не показывается**, выводится отчёт о расхождении |

Последняя строка главная: **самопроверка стоит до выдачи результата, а не после**.

```
d4-build2filter/

  selftest.html             самопроверка на эталонах
  src/resolve.js            разбор ссылки → идентификатор билда
  src/fetchBuild.js         чтение билда из открытой базы
  src/rules.js              сборка правил
  src/encode.js             protobuf + base64
  src/decode.js             разбор кода обратно
  src/checklist.js          чеклист для Switch 2
  data/meta-builds.json     карта коротких адресов
  data/affix-ids.json       id аффиксов
  data/type-ids.json        id типов вещей
  data/ui-labels.json       подписи меню игры
  .github/workflows/refresh-meta-builds.yml
  AFFIX-IDS.md              происхождение и проверка каждого id
  README.md                 как пользоваться, чего не умеет и почему

```

Никакой сборки и зависимостей, ничего минифицированного — исходник открывается на GitHub и
читается глазами. Это отдельное пожелание владельца.

**Публикация:** публичный репозиторий, GitHub Pages из ветки `main`, папка — корень.
Раздел «первичная настройка» — в `README.md`.

## 7. Решения, принятые за вас

1. **Читаем открытую базу d4builds напрямую**, а не страницу. Это тот же запрос, который
   делает их собственный сайт без всякой авторизации. Плюс: точнее и без закладок.
   Минус: если они закроют доступ, инструмент встанет.
2. **Карта витринных билдов обновляется задачей по расписанию, раз в сутки.** Чаще — незачем,
   реже — новые витринные билды будут ждать до суток.
3. **Результат кешируется в браузере на сутки** — вежливость к чужому серверу.
4. **Порог совпадения по умолчанию — 2 свойства.**
5. **Уровень пряток по умолчанию — «Мягкий».**
6. **Уникумы билда в v1 отдельно не подсвечиваются** — таблицы их id нет, выдумывать нельзя.
   Они видны по базовому правилу «показывать древние уникумы».
7. **Талисманы и осколки душ читаем, но в v1 не используем.**
8. **Имя репозитория — `d4-build2filter`.**
9. **Код из открытого генератора не копируется** (лицензия не указана), берём только числа
   со ссылкой на автора.
10. **Спека лежит в `docs/specs/`**, ближе к принятой у вас раскладке `docs/`.

## 8. Чего мы пока не знаем

- Не менялся ли формат кода между 13 и 15 сезоном. Проверяется первым кругом сверки.
- Как выглядит меню фильтра на Switch 2 — нужен ваш скриншот, иначе подписи в чеклисте
  будут выдуманы.
- Полон ли список из 77 аффиксов для 15 сезона.
- Как именно перечислить витринные билды для карты: список на главной рисуется в браузере,
  у задачи есть несколько путей его получить. Выбирается на шаге 2 работ.

## 9. Порядок работ

1. `git init`, каркас, `README.md` → проверка: репозиторий открывается на GitHub.
2. `resolve.js` + `fetchBuild.js` + карта витринных билдов → проверка: по ссылке на ваш
   Blazing Scream профиль собирается полностью, включая все слоты.
3. `encode.js` + `decode.js` + `selftest.html` → проверка: самопроверка зелёная, чужой
   рабочий код maxroll разбирается без ошибок.
4. `rules.js` + `index.html` → проверка: код собирается, самопроверка перед выдачей проходит.
5. Публикация на Pages → проверка: страница открывается с телефона по ссылке.
6. **Круг сверки на живой игре** → проверка: экспорт из игры совпадает с замыслом.
7. `checklist.js` + сверка подписей по вашему скриншоту Switch 2.

## 10. Что изменилось в версии 2

Версия 1 строилась вокруг кнопки-закладки: считалось, что статическая страница не сможет
достать билд из-за запрета межсайтовых запросов. Разведка показала, что это не так —
открытая база Firestore отдаёт документ билда кому угодно, с человеческими названиями
свойств внутри.

Поэтому: **закладка убрана целиком**, чтение билда переехало в саму страницу, добавились
карта коротких адресов и задача её обновления. Всё остальное — правило «прячем грубо, красим
точно», таблицы id, режим сверки, чеклист — осталось как было.
